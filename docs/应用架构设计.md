# 应用架构设计

## 设计目标

架构设计要服务于三个现实目标：

- Android MVP 能够快速交付
- 业务层在后续可迁移到 iOS 与 HarmonyOS
- 在不做复杂后端的前提下保证离线可用和数据可演进

## 总体原则

- 界面层与业务层分离
- 领域模型稳定优先于界面复用
- 本地数据优先于远程依赖
- 状态流转清晰，便于测试

## 推荐分层

### 表现层

负责页面、组件、状态展示和用户交互。

### 应用层

负责用例编排，例如：

- 创建房源
- 保存租房画像
- 生成 checklist 模板推荐
- 保存用户确认后的模板组合
- 新建看房记录
- 保存评分卡
- 生成对比结果
- 启动签约阶段
- 保存签约 checklist
- 保存签约材料
- 标记已签约或签约放弃

### 领域层

负责核心业务实体、规则与校验逻辑，例如：

- 评分计算
- 模板推荐规则
- 风险项判定
- 房源排序规则
- 对比摘要生成
- 看房阶段到签约阶段的流转规则
- 同一时间只允许一个活跃签约会话
- 签约终态判定

### 数据层

负责本地数据库、文件存储、导入导出和未来的同步接口。

## Android 端建议实现

- UI：Jetpack Compose
- 本地数据库：Room
- 后台任务：WorkManager
- 图片采集：CameraX
- 依赖注入：Koin 或 Hilt
- 序列化：kotlinx.serialization

## 模块建议

### `app`

平台入口、导航组装、依赖注入初始化。

### `feature-property`

房源相关页面和交互。

### `feature-viewing`

看房记录、看房检查项、照片与备注录入。

### `feature-compare`

评分、排序、对比与摘要展示。

### `feature-signing`

签约阶段入口、签约 checklist、签约材料、签约 AI 审查和终态确认。

### `domain`

实体、值对象、业务规则、用例接口。

### `data`

数据库、仓储实现、文件存储、导入导出。

### `core`

通用工具、错误模型、时间处理、资源封装。

## 多平台策略

### 当前阶段

仅交付 Android 应用，但从第一天起统一以下内容：

- 领域实体定义
- 看房/签约两套枚举与检查项编码
- 租房画像与模板推荐规则
- 评分算法
- 导出格式
- 媒体元数据结构

### 后续阶段

当 Android MVP 稳定后，再把 `domain` 与部分 `data` 能力抽为可共享模块，用于 iOS 与 HarmonyOS。

## 存储策略

### 结构化数据

使用本地数据库管理房源、看房记录、签约会话、评分、标签、对比状态等结构化信息。

### 媒体文件

看房照片与签约图片文件都与数据库分离存储，数据库只保存：

- 文件标识
- 存储路径
- 拍摄时间
- 关联房源
- 关联看房记录或签约会话
- 用户备注

## 同步预留

MVP 阶段不要求完整云同步，但要预留以下能力：

- 每个实体具备稳定主键
- 为未来同步保留更新时间字段
- 导出格式具备版本号
- 媒体文件与结构化数据可单独重建关联关系
- 阶段切换历史可被重建

## 测试策略

### 必测部分

- 评分计算逻辑
- 风险项判定逻辑
- 看房到签约的状态流转
- 单一活跃签约会话约束
- 导出结果生成
- 数据库迁移
- 关键页面状态恢复

### 后续补充

- UI 快照测试
- 导入导出兼容性测试
- 多平台一致性测试
